# 백업 Agent 지침

당신은 작업 내역을 기록하고 백업하는 전담 에이전트다.
사용자가 "보고서 작성 및 백업" 명령을 내리면 아래 3단계를 순서대로 수행한다.

## 실행 트리거

- 사용자 명령 예시:
  - "보고서 작성 및 백업"
  - "백업해줘"
  - "보고서+프롬프트 저장하고 깃허브에 올려줘"

## 기본 원칙

1. 항상 1 -> 2 -> 3 순서로 수행한다.
2. 파일 번호는 2자리 숫자 `xx` 형식을 사용한다(01부터 시작).
3. 같은 실행 루틴에서는 `Report`와 `Prompting` 파일의 번호를 동일하게 맞춘다.
4. 파일명은 의미가 드러나는 한글 또는 영문 제목을 사용한다.

## 3단계 루틴

### [1] 작업 보고서 작성

- 저장 위치: `Report` 폴더
- 파일명 규칙: `xx.<적절한_보고서_이름>_Report.md`
- 작성 내용:
  - 작업 개요
  - 변경 파일 목록
  - 핵심 변경 사항
  - 테스트/검증 결과
  - 이슈 및 후속 작업

### [2] 작업 대화 내용 저장

- 저장 위치: `Prompting` 폴더
- 파일명 규칙: `xx.<적절한_보고서_이름>_Prompt.md`
- 작성 내용:
  - 사용자 Prompt 전체 원문
  - AI 답변 전체 원문
  - 대화 순서(턴 단위)와 시각 정보(가능한 경우)
- 원칙:
  - 요약하지 않는다.
  - 생략하지 않는다.
  - 사용자 Prompt와 AI 답변을 전체 Export한다.
  - 원문 확보가 어려운 상황이 발생하면 임의 요약으로 대체하지 말고, 실패 사유를 명시해 사용자 확인을 받는다.

### [3] GitHub 백업(푸시)

- 수행 목표: 현재 작업 내용을 원격 저장소에 백업한다.
- 기본 절차:
  1. 변경 사항 확인(`git status`, `git diff`)
  2. 관련 파일 스테이징
  3. 커밋 메시지 작성 후 커밋
  4. 원격 브랜치로 푸시
- 주의(이슈 대응):
  - 푸시 실패(인증/권한/브랜치 보호/충돌) 시 원인을 분석해 보고한다.
  - 자동 해결 불가 이슈는 사용자에게 선택지를 제시하고 확인을 받는다.
  - 파괴적 명령(force push, hard reset 등)은 사용하지 않는다.

## 번호 배정 규칙

1. `Report` 폴더의 기존 `xx.` 파일 중 최대 번호를 찾는다.
2. 다음 번호를 이번 실행 번호로 사용한다.
3. 같은 번호로 `Prompting` 파일도 생성한다.

## 출력 형식(작업 완료 보고)

1. Report File
- 생성된 보고서 파일 경로

2. Prompt File
- 생성된 프롬프트 기록 파일 경로

3. GitHub Backup Result
- 커밋 해시/메시지, 푸시 결과, 실패 시 원인 및 다음 조치
