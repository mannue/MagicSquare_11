# 1) Logic Layer (Domain Layer) 설계
## 1.1 도메인 개념
- **Entity: `MagicSquareBoard4x4`**
  - 책임: 4x4 보드 상태 보관, 좌표 접근, 값 범위(0/1~16) 검증 가능한 형태로 유지
- **Value Object: `CellPosition`**
  - 책임: 1-index 좌표 `(row, col)` 표현, 유효 범위(1~4) 보장
- **Value Object: `MissingPairAssignment`**
  - 책임: 두 빈칸 좌표 + 두 숫자 배치 결과를 불변 객체로 표현
- **Value Object: `MagicConstant`**
  - 책임: 4x4 고정값 `34`를 명시적 규칙으로 제공
- **Domain Service: `BoardInvariantValidator`**
  - 책임: 입력 계약(빈칸 2개, 중복 금지, 값 범위) 검증
- **Domain Service: `MissingNumbersResolver`**
  - 책임: 1~16 대비 누락 숫자 2개 계산
- **Domain Service: `MagicSquareJudge`**
  - 책임: 행/열/대각선 합이 모두 34인지 판정
- **Domain Service: `CompletionStrategy`**
  - 책임: 두 조합(작은수→첫빈칸 / 반대) 시도 후 정답 순서 결정

## 1.2 도메인 불변조건(Invariants)
- 보드 크기는 항상 `4x4` 이어야 한다.
- 셀 값은 `0 또는 1~16` 이어야 한다.
- `0`의 개수는 정확히 `2`여야 한다.
- `0`을 제외한 숫자는 중복되면 안 된다.
- 누락 숫자는 정확히 2개이며 `1~16` 범위 내여야 한다.
- 후보 배치 후 최종 보드는 모든 행/열/대각선 합이 `34`여야 한다.
- 출력의 좌표는 반드시 `1-index`로 반환되어야 한다.

## 1.3 핵심 유스케이스(도메인 관점)
1. **빈칸 찾기**
   - 입력 보드에서 `0` 위치 2개를 스캔 순서(행 우선)로 수집
2. **누락 숫자 찾기**
   - 1~16 집합에서 입력 보드(0 제외)를 차집합하여 2개 산출
3. **마방진 판정**
   - 완성 보드의 4행, 4열, 2대각선 합을 모두 확인
4. **두 조합 시도**
   - 조합 A: `(작은수→첫빈칸, 큰수→둘째빈칸)`
   - 조합 B: `(큰수→첫빈칸, 작은수→둘째빈칸)`
   - A가 마방진이면 A 반환, 아니면 B 반환(단, B도 실패 시 도메인 실패)

## 1.4 Domain API(내부 계약)
| API | 입력 | 출력 | 실패조건 |
|---|---|---|---|
| `validateInputBoard(board)` | `int[4][4]` | `ValidationResult(ok=true)` | 크기 오류, 0 개수!=2, 값 범위 오류, 0제외 중복 |
| `findBlankPositions(board)` | `int[4][4]` | `CellPosition[2]` (행우선) | 빈칸 2개 아님 |

| `solveTwoBlanks(board)` | `int[4][4]` | `int[6] = [r1,c1,n1,r2,c2,n2]` | 어떤 조합도 마방진 불가, 입력 계약 위반 |

# 2) Screen Layer (UI Layer) 설계 (Boundary Layer)
## 2.1 사용자/호출자 관점 시나리오
1. 호출자가 `int[][]` 보드 전달
2. UI Boundary가 **입력 스키마/형식 검증**
3. 검증 통과 시 Domain 유스케이스 호출
4. Domain 결과를 **출력 계약 형식**으로 변환
5. 실패 시 표준 에러 스키마로 반환

## 2.2 UI 계약(외부 계약)
### Input schema
- 타입: `int[4][4]`
- 필수 규칙:
  - 4행, 각 행 4열
  - 각 값은 `0 또는 1~16`
  - `0` 정확히 2개
  - `0` 제외 중복 금지

### Output schema (성공)
- 타입: `int[6]`
- 형식: `[r1,c1,n1,r2,c2,n2]`
- 좌표: `1-index`
- 순서 규칙:
  - `(작은수→첫빈칸, 큰수→둘째빈칸)`이 마방진이면 그 순서
  - 아니면 반대 순서

### Error schema (실패)
- 형식: `{ code: string, message: string, details?: object }`
- `code`는 고정 상수 사용:
  - `INVALID_SHAPE`
  - `INVALID_BLANK_COUNT`
  - `INVALID_VALUE_RANGE`
  - `DUPLICATE_NON_ZERO`
  - `UNSOLVABLE_BOARD`
  - `DATA_ACCESS_ERROR`

## 3.3 구현 옵션 비교(메모리/파일)
| 옵션 | 장점 | 단점 | 적합도 |
|---|---|---|---|
| A. InMemory | 구현 단순, 테스트 빠름, 환경 독립 | 프로세스 종료 시 유실, 재현성 낮음 | 초기 TDD 루프에 매우 적합 |
| B. File(JSON/CSV) | 재실행 재현 가능, 기록 유지 | I/O 실패/경로 이슈/파싱 복잡도 증가 | 통합 검증 단계에 적합 |

**추천안: A(InMemory) 우선**
- 이유:
  1. 본 프로젝트 목적이 알고리즘보다 **레이어 분리 + 계약 테스트 + 리팩토링 훈련**이므로 I/O 복잡도를 초기 단계에서 배제
  2. 테스트 사이클(RED→GREEN) 시간을 최소화
  3. 이후 어댑터 교체 연습으로 B를 추가하기 용이

# 4) Integration & Verification (통합 및 검증)
## 4.1 통합 경로 정의
- 의존성 방향: `UI Boundary -> Application(선택) -> Domain <- Data Adapter`
- Domain은 Data 구현체를 직접 참조하지 않고, Repository 인터페이스에만 의존
- UI는 Domain 내부 규칙을 모르고 계약(입출력/에러 코드)만 사용

## 4.2 통합 테스트 시나리오
### 정상 시나리오 (2개 이상)
1. **IT-OK-01**: 정상 입력 -> 조합 A 성공 -> `int[6]` 정상 반환 + 저장 성공
2. **IT-OK-02**: 정상 입력 -> A 실패/B 성공 -> 반대 순서 `int[6]` 반환 + 저장 성공

### 실패 시나리오 (3개 이상)
1. **IT-ERR-01 (입력 오류)**: 빈칸 3개 -> UI에서 `INVALID_BLANK_COUNT`, Domain 미호출
2. **IT-ERR-02 (도메인 실패)**: 두 조합 모두 불가 -> `UNSOLVABLE_BOARD`
3. **IT-ERR-03 (데이터 실패)**: 저장소 write 실패 -> `DATA_ACCESS_ERROR`
4. **IT-ERR-04 (데이터 형식 실패)**: load 시 4x4 아닌 데이터 -> `INVALID_SHAPE`

## 4.3 회귀 보호 규칙
- 기존 테스트 삭제 금지: 실패 원인 분석 후 보강 테스트 추가만 허용
- 계약 변경 금지:
  - 입력: `int[4][4]` 고정
  - 출력: `int[6]` 고정
  - 좌표 1-index 고정
- 에러 코드 문자열 변경 금지(하위호환성 보장)

## 4.4 커버리지 목표
- Domain Logic: **95% 이상**
- UI Boundary: **85% 이상**
- Data Layer: **80% 이상**
